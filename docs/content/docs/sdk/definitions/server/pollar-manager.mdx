Pollar — social login and the custodial wallets behind it — `client.pollar`. The login is a three-legged flow, and the middle leg is the one that surprises people: the browser leaves for the provider and comes back to POLLAR, not to you, so a client cannot simply await a redirect. It polls instead. 1. `authorize()` → a `state` and the `authorization_url` to open. 2. `session(state)` until `status` is `authorized`, which carries a bridge `code`. 3. `token({ code, code_verifier })` → the session, its wallets and the profile. Use PKCE. The code travels through a redirect a client does not control, and the `code_verifier` is the only reason an intercepted one is worth nothing. The two callback routes (`/oauth/callback…`) are deliberately absent from this manager: they are where a BROWSER lands, not something a server calls. Polling `session()` is the programmatic half of the same step.
