---
title: Webhooks P2P
description: Les événements envoyés par les ordres, encaissements et versements P2P, qui reçoit chacun et ce que contient leur payload.
---

Les événements P2P passent par les mêmes endpoints de webhook que tous les événements de Cosmos Pay,
signés de la même manière. Enregistrez un endpoint dans le tableau de bord, sous **Webhooks**, ou
avec l'API, et choisissez les événements ci-dessous.

## Événements

| Événement | Envoyé quand |
| --- | --- |
| `P2P_ORDER_CREATED` | Un ordre s'est ouvert sur la chaîne. |
| `P2P_ORDER_ACCEPTED` | Un marchand a accepté une vente ou un versement et bloqué sa caution. Les achats et les encaissements sautent cette étape. |
| `P2P_ORDER_PAID` | Le côté acheteur a marqué l'ordre comme payé. |
| `P2P_ORDER_COMPLETED` | Le vendeur a libéré. L'acheteur a reçu les jetons. |
| `P2P_ORDER_CANCELLED` | L'ordre a été annulé. Les jetons sont revenus au vendeur. |
| `P2P_ORDER_EXPIRED` | Une échéance est passée. Les jetons sont revenus au vendeur. |
| `P2P_ORDER_DISPUTED` | Une partie a ouvert un litige. |
| `P2P_ORDER_RESOLVED` | L'arbitre a tranché le litige. |
| `P2P_ORDER_FAILED` | L'ordre ne s'est jamais ouvert. |
| `P2P_CHARGE_SUCCEEDED` | Un ordre qui paie un encaissement a abouti. Un encaissement multi-usage en envoie un par ordre qui le paie. |
| `P2P_PAYOUT_BATCH_COMPLETED` | Tous les ordres d'un lot de versements sont terminés. |

Les ordres aboutis, annulés, expirés, tranchés et échoués, les encaissements réussis et les lots
terminés sont définitifs : aucun autre événement ne les suit.

## Qui les reçoit

Les événements d'un ordre parviennent à deux parties : le client qui l'a ouvert et le marchand auquel
il a été apparié, lorsqu'il s'agit d'organisations différentes. `data.role` indique laquelle vous
êtes, et chacune ne reçoit que sa propre vue de l'ordre.

| `data.role` | Le payload contient | Il ne contient jamais |
| --- | --- | --- |
| `client` | Les montants, les adresses, les échéances, les hashs de transaction et le statut de l'ordre, le nom affiché et l'historique du marchand, et vos propres `externalReference`, `chargeId` et `payoutBatchId` | Les coordonnées de paiement, l'identité du payeur ou le compte d'un bénéficiaire |
| `merchant` | Les montants, les adresses, les échéances, les hashs de transaction et le statut de l'ordre, avec vos `merchantAccountId` et `merchantSide` | Les coordonnées de paiement, l'identité du payeur, le compte d'un bénéficiaire ou les références propres du client |

Lisez l'ordre via l'API pour ce qu'un webhook laisse de côté : `GET /v1/p2p/orders/{id}` en tant que
client, `GET /v1/p2p/merchant/orders/{id}` en tant que marchand.

Utilisez `id` pour traiter chaque événement une seule fois. Relisez l'ordre avec l'API avant de faire
bouger de l'argent : un événement vous dit que quelque chose a changé ; l'ordre vous dit où il en est.

## Vérifiez la signature

Chaque envoi porte `X-Cosmos-Signature: t=<unix seconds>,v1=<hex>`, un HMAC-SHA256 de
`<t>.<raw body>` avec le secret de votre endpoint. Vérifiez-le sur le corps brut avant de vous fier à
l'événement. Le SDK le fait pour vous : voir [Webhooks](/sdk/server/webhooks/).
